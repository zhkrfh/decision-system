# EVOS 使用说明

> 自我进化操作系统 · 2026-10-10 建立
> 架构见 `docs/自我进化操作系统架构_v1.0.md`

---

## 这是什么

一个**增量叠加层**，不是新系统。它包裹现有的 dispatcher、内容状态机、git 仓库，不侵入任何已有代码。

## 目录

```
EVOS/
  experience.jsonl    ← 环1-2：经验库（每行一条 JSON）
  skills/             ← 环3：已固化的执行规则（待作者批准后写入）
  README.md           ← 本文件
```

---

## 四环流程

```
捕获 → 提炼 → 晋升 → 回验
 ↑                    ↓
 └────────────────────┘
```

### 环 1 · 捕获（自动）

触发源：命令报错 / 用户纠正 / 预测失效 / 平台故障 / 反直觉发现

**捕获必须自动**。靠人写复盘的系统三个月后就死了。

### 环 2 · 提炼（AI）

从原始事件提取 `root_cause`（真实原因，非表面现象），生成 `rule_candidate`。

**归因质量决定规则质量。** 例：微信返回 40007 的根因不是「接口报错」，而是「AppSecret 与 AppID 不匹配」。

### 环 3 · 晋升（有门槛）

| 阶段 | 条件 | 行为 |
|------|------|------|
| observing | 首次记录 | 只记录，不影响行为 |
| trialing | 观察到 ≥2 次且根因明确 | 影响行为，**主动告知正在试行** |
| codified | 试行无复发，或复现 ≥3 次 | 永久规则 |
| rolled_back | 固化后仍致同类错误 | 自动降级并标记 |

**晋升不自动到 codified。** 必须过试行期，且试行期显式告知。

### 环 4 · 回验（决定生死）

每周度量：

| 指标 | 定义 | 目标 |
|------|------|------|
| 复发率 | 同 root_cause 在 90 天内再次出现次数 | 持续下降 |
| 规则有效性 | 固化规则中实际触发且有效的比例 | > 70% |
| 净收益 | 自动化节省时间 − 维护成本 | 持续为正 |

**90 天未触发且未验证有效的规则 → 归档。**
**导致 ≥2 次新错误的规则 → 立即回滚。**

> 只进不出的记忆库会无限膨胀，最终无法检索。归档是维护，不是失败。

## 记忆分层与隔离

| 层 | 位置 | 生命周期 | 谁能改 |
|----|------|---------|-------|
| L1 执行记忆 | `EVOS/experience.jsonl` | 日级滚动 | AI 自动 |
| L2 技能规则 | `EVOS/skills/*.md` | 月级复审 | AI 建议 + 作者批准 |
| L3 项目规范 | `正典仓库/docs/` | 版本化 | 作者签署 |
| **L4 理论口径** | 冻结版本文档 | **作者独占** | **仅作者** |

**隔离纪律**：L1/L2 的进化**永远不能自动升格到 L3/L4**。

> 这是自我进化系统最大的危险：系统会为了省事，悄悄把未验证的理论「优化」掉。

## 演化能力三级判据

| 级别 | 判据 | 状态 |
|------|------|------|
| L1 记录型 | 能记住发生过什么 | ✅ 已具备 |
| L2 调整型 | 能根据经验改变行为 | ⚠️ 需手动触发 |
| L3 演化型 | 自动发现「该改什么」并验证有效性 | ❌ 未具备 |

**目标：三个月内达到 L3。**

---

## 每周复盘仪式

固定在**周日 20:00**（与既有数据回填任务合并）。

四个问题：

1. 本周新增了哪些经验？哪些该晋升？
2. 有哪些规则被触发？有效吗？
3. 复发率是升是降？
4. 有没有规则该归档或回滚？

---

## 防护机制

| 风险 | 防护 |
|------|------|
| 记忆库膨胀 | 90 天归档 + 分层 |
| 错误规则固化 | 试行期 + 回滚通道 |
| 理论被污染 | L4 物理隔离 + 作者独占 |
| 进化噪声 | 晋升门槛 |
| 过度自动化 | 关键节点保留人工签署 |
