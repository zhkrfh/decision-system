# 自我进化操作系统架构 v1.0（EVOS）

> 生成时间：2026-10-10
> 定位：轨道二（快变量，日级迭代）
> 目标：让执行成本持续趋零，让系统在使用中自己变强
> 命名：EVOS = Evolution Operating System

---

## 一、现状诊断：已有雏形，但只记录不演化

灵犀侧已存在两个相关技能：

| 技能 | 实际能力 | 局限 |
|------|---------|------|
| `self-improvement` | 把错误/纠正/洞察追加到 `learnings_log` | **纯记录**。经验写了就躺在那里，不会影响下次行为 |
| `skill-evolution-manager` | 会话复盘后把 JSON 合并进 `evolution.json` | **半自动**。需手动触发，且不做有效性验证 |

**共同缺陷**：都是**追加式日志**，不是**闭环系统**。缺三样东西：

1. **无晋升门槛** —— 什么样的经验值得固化成永久规则？当前是「都记下来」
2. **无失效淘汰** —— 三个月前的经验可能已过时，但永不清理
3. **无效果回验** —— 固化的规则是否真的减少了错误？从不测量

> 项目志里已有一条同源纪律：**「踩坑当夜固化」**。EVOS 是把这条纪律从人工执行升级为系统自动执行。

## 二、EVOS 四环架构

```
    ┌──────────────────────────────────────┐
    │  环 1 · 捕获 Capture                 │  一切经验自动入库
    │  错误 / 用户纠正 / 失效预测 / 新需求   │  不靠人记得写
    └───────────────┬──────────────────────┘
                    ↓
    ┌──────────────────────────────────────┐
    │  环 2 · 提炼 Distill                 │  噪声 → 知识
    │  结构化 · 去重 · 归因 · 判定严重度    │  AI 完成
    └───────────────┬──────────────────────┘
                    ↓
    ┌──────────────────────────────────────┐
    │  环 3 · 晋升 Promote                 │  知识 → 规则
    │  观察期 → 试行 → 固化 → 回滚通道     │  有门槛，非自动
    └───────────────┬──────────────────────┘
                    ↓
    ┌──────────────────────────────────────┐
    │  环 4 · 回验 Verify                  │  规则 → 有效性证据
    │  同类错误复发率 · 净收益 · 淘汰       │  决定生死
    └───────────────┬──────────────────────┘
                    │
                    └──→ 回到环 1（有效则巩固，失效则淘汰）
```

### 环 1 · 捕获（自动）

**触发源**（无需人工干预）：

| 事件 | 检测方式 |
|------|---------|
| 命令报错 | bash 非零退出 / 异常栈 |
| 用户纠正 | 消息中出现「不对」「不是」「错了」「重做」等语义信号 |
| 预测失效 | 战绩板验证日期到达，结果为「未命中」 |
| 平台故障 | API 返回 4xx/5xx、限流、验证码 |
| 反直觉发现 | 同一操作连续 3 次结果不一致 |

**关键设计**：捕获必须是**自动的**。靠人写复盘的系统，三个月后就死了。

### 环 2 · 提炼（AI 完成）

把原始事件转为结构化条目：

```json
{
  "id": "EVOS-20261010-001",
  "type": "error | correction | failure | insight | feature",
  "severity": "low | medium | high | critical",
  "context": "在什么场景下发生",
  "root_cause": "真实原因（不是表面现象）",
  "rule_candidate": "应固化为规则的表述",
  "evidence": ["支撑证据"],
  "scope": "global | project | task",
  "observed_count": 1
}
```

**归因是这一步的核心**。例：微信开发者返回 40007，不是「接口报错」，而是「AppSecret 与 AppID 不匹配」——**根因写错，规则就写错**。

### 环 3 · 晋升（有门槛）

**四阶段晋升路径**：

| 阶段 | 条件 | 状态 |
|------|------|------|
| 观察 | observed_count = 1 | 只记录，不影响行为 |
| 试行 | 观察到 ≥2 次，且根因明确 | 影响行为，但会主动告知「正在试行此规则」 |
| 固化 | 试行期无复发，或复现 3 次以上 | 成为永久规则 |
| 回滚 | 固化后仍导致同类错误 | **自动降级并标记** |

> **纪律：晋升不自动到「固化」。** 必须经过试行期，且试行期要显式告知，避免悄悄改变行为。

### 环 4 · 回验（决定生死）

**每周度量三个指标**：

| 指标 | 定义 | 目标 |
|------|------|------|
| 复发率 | 同一 root_cause 在 90 天内再次出现的次数 | 持续下降 |
| 规则有效性 | 固化规则中实际被触发且有效的比例 | > 70% |
| 净收益 | 自动化节省的人工时间 − 维护成本 | 持续为正 |

**淘汰机制**：90 天未触发且未验证有效的规则 → 归档；导致 ≥2 次新错误的规则 → 立即回滚。

> **多数「自我进化」系统失败的原因是只进不出。** 记忆库无限膨胀，最终无法检索。**归档不是失败，是维护。**

## 三、记忆分层（与理论轨道隔离）

**关键原则**：系统记忆与理论口径**物理隔离**。

| 层 | 存放位置 | 生命周期 | 谁能改 |
|----|---------|---------|-------|
| L1 · 执行记忆 | `EVOS/experience.jsonl` | 日级滚动 | AI 自动 |
| L2 · 技能规则 | `EVOS/skills/*.md` | 月级复审 | AI 建议 + 作者批准 |
| L3 · 项目规范 | `正典仓库/docs/` | 版本化 | 作者签署 |
| L4 · 理论口径 | 冻结版本文档 | **作者独占** | **仅作者可改** |

**隔离纪律**：
- L1/L2 的进化**永远不能自动升格到 L3/L4**
- L3/L4 的变更必须作者签署，且留痕
- 理论验证只用**已冻结口径**，禁止用工程迭代中的中间结论

> **否则系统会为了省事，悄悄把未验证的理论「优化」掉。** 这是自我进化系统最大的危险。

## 五、EVOS 与 OPC 的关系

| OPC 环节 | EVOS 提供什么 |
|---------|--------------|
| 内容生产 | 每次写作的经验沉淀（哪类钩子有效） |
| 平台分发 | 平台故障模式库（风控/验证码/弹层变化的应对） |
| 交付服务 | 客户问题的归类与标准应答 |
| 决策体系 | **不参与**（L4 隔离） |

**核心价值**：你现在所有踩坑都是**一次性收益**（解决了就不再犯，但也没系统性变强）。EVOS 把它们变成**累积性资产**。

## 七、演化能力的三级判据

一个系统是否真的在进化，看三个指标：

| 级别 | 判据 | 当前状态 |
|------|------|--------|
| L1 记录型 | 能记住发生过什么 | ✅ 已具备 |
| L2 调整型 | 能根据经验改变行为 | ⚠️ 半自动（需手动触发） |
| L3 演化型 | 能自动发现「该改变什么」并验证有效性 | ❌ 未具备 |

**目标：三个月内达到 L3。**

## 八、风险与防护

| 风险 | 后果 | 防护 |
|------|------|------|
| 记忆库膨胀 | 无法检索，系统变笨 | 归档机制 + 分层 |
| 错误规则固化 | 反复犯错且不自知 | 试行期 + 回滚通道 |
| 理论被系统污染 | 未验证理论被静默修改 | L4 物理隔离 + 作者独占 |
| 进化噪声 | 每次失败都改规则，规则泛滥 | 晋升门槛 + 90 天归档 |
| 过度自动化 | 失去判断 | 关键节点保留人工签署 |
